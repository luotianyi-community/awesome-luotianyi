## About

Luo Tianyi (洛天依) is China's first virtual singer, launched in 2012 by Shanghai Huanian Information Technology Co., Ltd. (Vsinger). Around her grew a distinctive ecosystem of fan-made tooling, models, themes and creative projects — most of it scattered across GitHub. This repository indexes that ecosystem.

**This is an unofficial community index. It is not affiliated with or endorsed by Vsinger.**

## Inclusion criteria

A repository is listed only if it satisfies **all** of the following:

1. **Explicitly related**: the repository name, description, README or topics contain one of 洛天依 / 乐天依 / 天依 / Luo Tianyi / LuoTianyi / Vsinger / 天依craft.
2. **Real content**: the repository is non-empty and the code or data itself relates to Luo Tianyi — not merely owned by an account named "luotianyi".
3. **Accessible**: the repository is not archived (archived repositories are excluded automatically).

Bonuses: a README, a LICENSE, a commit within the last 12 months, stars ≥ 3.

**Not accepted**: personal homepage dumps, empty repositories, name collisions (e.g. `LuoTianyi-arm64/printrgb`, which is a terminal colorizer unrelated to Luo Tianyi), and projects that merely link to an unrelated site. Full rubric: [docs/CRITERIA.md](docs/CRITERIA.md).

## List policy

Every repository the automation encounters ends up in exactly one of four states, and **once decided, it is never proposed again**:

| State | Meaning | File | Re-proposed? |
| --- | --- | --- | --- |
| `listed` | included | `data/entries/listed.json` | no |
| `excluded` | technically excluded (archived / empty / fork / no relevant signal) | `data/entries/excluded.json` | no |
| `rejected` | rejected by a maintainer, with a reason | `data/entries/rejected.json` | no |
| `candidate` | awaiting a decision | `data/candidates/queue.json` | yes — an issue is opened |

- The primary key is the **numeric GitHub repository id**; `full_name` is display only. Renames and transfers never create duplicates — the old name is kept in `aliases`.
- Each run scans for suspect repositories, recent commits and issues, scores them, and opens an issue **only for repositories never seen before**.
- Maintainers decide inside the issue with one of: `/approve <category-id>`, `/reject <reason>`, `/exclude <reason>`.
- Only users with `write` permission on this repository can decide.
- At most 20 candidate issues per run, at most 4 per owner.
- Rejections can be reviewed; overturning requires two maintainers including the Lead, and the original record is kept. See [docs/GOVERNANCE.md](docs/GOVERNANCE.md).

## Automation

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `catalog-sync` | every 6h / manual | search GitHub → score → dedupe into queue → render README → validate → commit |
| `radar` | hourly / manual | recent commits and issues/PRs → map back to repositories → open candidate issues |
| `triage` | issue comment | parse `/approve` `/reject` `/exclude`, write the registry, close the issue |
| `ci` | PR / push | unit tests, README freshness, `validate` |

```bash
node --test "tests/*.test.mjs"
node scripts/validate.mjs
node scripts/render-readme.mjs
node scripts/scan-catalog.mjs --dry-run --pages 1   # needs GITHUB_TOKEN
```
