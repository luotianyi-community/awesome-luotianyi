# 收录标准细则（CRITERIA）

本文档是 [GOVERNANCE.md](./GOVERNANCE.md) 中“评分与阈值”的展开：**什么仓库能进这张清单，什么仓库不能**。标准写成判定表，是为了让裁决可复现——同一仓库换一个人判断，结论应当相同。

## 1. 一句话标准

**仓库必须以洛天依（Luo Tianyi / 洛天依 / 天依 / Vsinger 中文V家）为主题或明确相关，且非空、有实际内容。**

两个条件缺一不可：

- **主题性**：不是“顺便提到”，而是这个仓库存在的理由是洛天依或与她直接相关；
- **实质性**：不是空壳、不是占位、不是只有一句 README 的脚手架。

判定顺序永远是：先看排除项（一票否决），再看必须满足项（全部通过），最后才看加分项（决定排序，不决定收录）。

## 2. 判定流程

```text
拿到 owner/repo
  |
  +-- 1) 命中任何排除项？ --是--> excluded（技术性）或 rejected（人工判断），结束
  |
  +-- 2) 必须满足项全部通过？ --否--> rejected（理由：相关性不足），结束
  |
  +-- 3) 能归入 9 类之一？ --否--> 先讨论是否新增分类，暂不收录
  |
  +-- 4) 通过 --> /approve <category-id>，写 evidence，结束
```

## 3. 必须满足项（全部满足才可能收录）

以下每一条都是**硬性条件**，缺一条就不收录。判定时请写下你依据的具体位置，这就是 `evidence` 字段。

| # | 条件 | 如何核验 | 不满足时 |
| --- | --- | --- | --- |
| M1 | 仓库描述（About）或 README 中**明确出现** `洛天依` / `Luo Tianyi` / `LuoTianyi` / `天依` / `Vsinger` 之一 | 打开仓库首页看 About；在 README 中搜索上述关键词，记录原文 | 否决 |
| M2 | 上述关键词出现在**主题位置**：仓库名、About、README 标题或首个段落、或核心资源文件名 | 不是出现在最底部致谢、License 段、依赖清单的注释里 | 否决 |
| M3 | 仓库**非空**：至少有实际的代码、配置、模型、文档或素材文件（`size > 0` 且存在非模板文件） | 看文件树，不是只有 README/LICENSE/.gitignore | `excluded`，理由 `empty repository` |
| M3b | 仓库**不是 fork**（或者是 fork 但有独立、实质的改动） | 页面标题下是否显示 “forked from”；若是 fork，看是否有超出上游的提交与内容 | `excluded`，理由 `fork without independent work` |
| M4 | 仓库**未归档** | 页面顶部是否有 “This repository has been archived” 横幅 | `excluded`，理由 `archived` |
| M5 | 仓库**公开可访问**，无需登录即可看到内容 | 用未登录窗口打开确认 | `excluded`，理由 `deleted or private` |
| M6 | 内容与该主题的结合是**项目主体**，而非附带提到 | 删掉洛天依相关部分后，项目是否还成立？如果不成立，就是主题性项目 | 否决 |
| M7 | 不违反 [NOTICE.md](../NOTICE.md) 与 [CODE_OF_CONDUCT.md](./CODE_OF_CONDUCT.md) 第 5 节：内容主体不是未授权资源的分发 | 看仓库是否以打包分发他人模型/音源/美术素材为主要目的 | `rejected`，理由 `unauthorized redistribution` |

**关于 M1 的“明确出现”**：必须是字面命中，不接受推理。

- 不算：仓库里有一张动漫女孩图，推测是洛天依；
- 不算：owner 名叫 `luotianyi`，但仓库内容毫无关联（这是名字碰撞）；
- 不算：LICENSE 里的版权人名字恰好包含该字符串；
- 算：`assets/洛天依/` 目录、`luotianyi.model3.json`、About 写 “洛天依桌面宠物”。

## 4. 加分项（不影响是否收录，只影响排序）

命中越多，条目在 README 同类中的排序越靠前，**但不会把不满足必须项的项目救回来**。

| # | 加分项 | 权重 | 说明 |
| --- | --- | --- | --- |
| P1 | 有可读的 README（说明用途、安装、使用） | 中 | 只有一句 “TODO” 不算 |
| P2 | 有明确的 LICENSE 文件 | 中 | 无许可证的仓库仍可收录，但会在描述中提示“未声明许可证” |
| P3 | 最近 12 个月内有提交 | 中 | 用 `pushed_at` 判定；超 12 个月不排除，只降序 |
| P4 | star ≥ 3 | 低 | 3 是“有别人真的用过”的最低信号；低于 3 仍在候选内，但不因 star 高而免检 |
| P5 | 有可运行的示例或截图 | 低 | 帮助读者判断是否可用 |

注意 star 的实际作用：**star 高不能抵消排除项**。一个 3000 star 的通用工具，只因标题里有 “Tianyi” 而被误命中，仍然是 `excluded`。

## 5. 排除项（命中任一项即排除）

| # | 排除项 | 判定信号 | 状态与理由 |
| --- | --- | --- | --- |
| E1 | 仓库已归档（archived） | 归档横幅 | `excluded`，`archived` |
| E2 | 空仓库（size = 0，或只有模板文件） | 文件树为空或仅 `README.md` 一行标题 | `excluded`，`empty repository` |
| E3 | fork 且无独立改动 | “forked from”，提交数不超上游 | `excluded`，`fork without independent work` |
| E4 | 纯个人主页 / Profile 仓库（`owner/owner`、`owner/.github`） | 仓库名等于 owner 名 | `excluded`，`profile repository` |
| E5 | 名字碰撞：owner 或仓库名含 `luotianyi`，但内容与本主题无关 | 见第 7 节案例 | `excluded`，`name collision` |
| E6 | 仅 URL / 描述中的链接命中（如提到 `luotianyi.vc`），正文无关 | 关键词只在链接或探测地址中出现 | `excluded`，`incidental url match` |
| E7 | 以分发未授权资源为主体 | 打包他人模型/音源/美术素材 | `rejected`，`unauthorized redistribution` |
| E8 | 恶意或明显有害（窃取凭据、挖矿、伪装的投毒项目） | 需技术证据 | `excluded`，`malicious`，并按 SECURITY.md 6.2 处理 |
| E9 | 不是仓库（组织页、User 页、Gist、Release 页、镜像站地址） | URL 形态不对 | 直接关闭 Issue，不建状态 |
| E10 | 与主题相关但完全不可用（无代码、无文档、仅占位说明） | 实质等同空仓库 | `excluded`，`nousable content` |

## 6. 分类判定

收录时必须指定**一个**分类，id 原样使用：

| id | 中文名 | 典型内容 | 易混淆点 |
| --- | --- | --- | --- |
| `desktop-pet` | 桌面宠物与看板娘 | 桌宠、屏幕挂件、状态栏看板娘 | 与 `live2d` 的区别：这里侧重“挂在桌面”，不要求用 Live2D |
| `live2d` | Live2D 模型与网页插件 | 模型仓库、加载器、网页挂件 | 纯静态立绘不算 Live2D |
| `tts-ai` | 语音合成与对话 AI | TTS 引擎、语音包、对话机器人、LLM 人格 | 与 `audio-assets` 的区别：这里产出“会说话的”，不是“素材” |
| `theme-skin` | 主题·美化·壁纸 | 编辑器主题、系统主题、壁纸包、图标 | — |
| `data-tools` | 数据·知识库·工具链 | 数据集、百科、歌词库、抓取/整理工具 | 纯爬虫无数据产出归此类 |
| `game-mod` | 游戏·模组·硬件二创 | 游戏模组、Minecraft 皮肤、单片机/硬件项目 | 硬件玩具也归此类 |
| `audio-assets` | 音频·乐谱·创作素材 | UST/VSQX 工程、乐谱、伴奏、MIDI、采样素材 | 与 `tts-ai` 的区别：素材不实时生成语音 |
| `community-site` | 社区站点与周边服务 | 导航站、BBS、图床、周边商店索引、活动站 | 站点本身需与主题直接相关 |
| `docs` | 教程与文档 | 入门教程、调教指南、技术说明、翻译文档 | 单篇博客不收录，成体系的文档才收 |

一个仓库只能归一类。若同时符合两类，选“主要用途”对应的那一类，并在 Issue 中说明为什么另一个不合适。

## 7. 边界案例

以下是真实出现过的误命中类型，直接给出结论，便于对照：

### 案例 1：`Luotianyi-0712/cto`

- **现象**：owner 名为 `Luotianyi-0712`，仓库是一个 OpenAI API 反向代理（`cto`），代码与文档中无任何洛天依相关内容。
- **判定**：`excluded`，理由 `name collision`（E5）。
- **依据**：M1 不满足——主体内容里没有主题词，只有 owner 名命中。owner 名不是仓库主题。
- **附带说明**：即便这个 owner 确实是某位洛天依爱好者，仓库本身与该主题无关，仍不收录。人不重要，仓库内容重要。

### 案例 2：`api-evangelist/luotianyi`

- **现象**：第三方 API 档案项目自动生成的一批 “某服务的 API 说明” 仓库之一，仓库名含 `luotianyi`，内容是通用的 API 描述模板。
- **判定**：`excluded`，理由 `incidental url match`（E6）或 `name collision`（E5）。
- **依据**：M1 字面或许命中（标题里有），但 M2 不满足——关键词不在主题位置，也不是项目的存在理由；M6 判定为“删掉关键词后项目依然成立”。
- **延伸**：这类自动生成的档案仓库数量多、内容同质，若被收录会显著拉低清单质量。

### 案例 3：`LuoTianyi-arm64/printrgb`

- **现象**：owner 名为 `LuoTianyi-arm64`，仓库是一个终端彩色打印小工具，README 与代码中无任何洛天依内容。
- **判定**：`excluded`，理由 `name collision`（E5）。
- **依据**：典型的名字碰撞——用户名与该角色同音/同名，但项目是通用工具。
- **判定要点**：看 README 首屏和 About。都无关就该干脆利落地排除，不必逐文件翻查。

### 案例 4：`SoraKasvgano/YaheiPHP7ProbeByLuminous`

- **现象**：一个 PHP 探针/备份工具，仅在仓库描述中的链接地址提到了 `luotianyi.vc`（某个站点域名），仓库正文与该主题无关。
- **判定**：`excluded`，理由 `incidental url match`（E6）。
- **依据**：M1 的“明确出现”被放宽成了“出现在一个 URL 里”，不满足 M2。域名归属与仓库主题是两件事。
- **补充**：如果该仓库的主要功能确实是为某个洛天依相关站点服务（而不是通用的探针脚本），则可能满足 M6，需按第 8 节的口径重新评估。

### 案例 5：通用工具附带主题皮肤（反向边界）

- **现象**：一个通用终端提示符主题框架，额外提供了一个洛天依配色主题文件 `themes/luotianyi.toml`。
- **判定**：`rejected`，理由 `incidental theme`（相关性不足）。
- **依据**：主题文件确实存在（M1、M2 部分满足），但 M6 不满足——删掉该主题文件，项目完全成立，且主体是通用框架。
- **这类情况怎么帮上忙**：如果存在一个“只包含洛天依主题集合”的仓库，那才是应该被收录的对象。

## 8. 常见争议的判定口径

裁决时最容易吵起来的几类，给出统一口径，减少来回：

| 争议 | 口径 |
| --- | --- |
| “README 只提了一次，算不算？” | 看**位置**不看次数。标题/首段/About 中出现一次即可；只在末尾致谢中出现十次也不算 |
| “作者说是给洛天依做的，但仓库里看不出来” | 以仓库内可核验内容为准。作者声明可以写进 `evidence` 作为补充，但不能替代文件证据 |
| “仓库很烂但确实是主题项目” | 质量不是收录标准。收录后可在 `desc` 中如实描述其状态（如“早期原型，功能不完整”） |
| “仓库很好但与主题只是弱相关” | 弱相关不收。清单的价值在于窄，不在于多 |
| “同一作者的多个仓库” | 按仓库逐个判定，不存在“收录一个就带一批”。若其中某几个是同一项目的拆分（如 core + theme），可分别收录并在描述中说明关系 |
| “已收录仓库后来删掉了洛天依相关内容” | 状态改为 `excluded`，理由 `no longer relevant`，并在 changelog 记录。不转 `rejected`——这不是否决，是失效 |
| “仓库改名成完全无关的名字” | 只更新 `full_name` 与 `aliases`，状态不变 |
| “仓库转移到了另一个 owner” | 同上。数字 id 不变即同一仓库 |
| “fork 了上游但加了很多主题内容” | 若主题内容是其独立新增（M3b 通过），可收录；描述中注明 fork 关系 |

## 9. 排除与否决的选择

两者都是“不收录”，但后果不同（详见 [GOVERNANCE.md](./GOVERNANCE.md) 第 2、4 节）。选择规则：

| 情形 | 选择 | 理由 |
| --- | --- | --- |
| 客观状态导致不可用（archived、空、fork、私有无权限） | `exclude` | 状态可变化，将来可能翻案 |
| 内容客观无关（名字碰撞、URL 误命中、通用工具） | `exclude` | 这是事实判断，不是价值判断 |
| 相关性有争议，一时说不清 | `exclude`（理由写 `under review`） | 保留后续讨论空间 |
| 明确判定为与主题无关，且已充分核实 | `reject` | 表达“这个方向的提名不要再来了” |
| 违规定（未授权资源分发、恶意） | `reject` 或 `exclude`（恶意用 `exclude` + `malicious`） | 需按 SECURITY 流程处理 |
| 权利人要求下架 | 直接移出，记 `rights-takedown` | 不辩论，立即执行 |

原则：**拿不准就用 `exclude`**。`rejected` 应留给“已经想清楚了的否定”，而不是“暂时没想清楚的否定”。
