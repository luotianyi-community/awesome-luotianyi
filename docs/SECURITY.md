## 1. 威胁模型：本项目不做什么

先说清楚边界，避免误报：

| 事实 | 含义 |
| --- | --- |
| **本仓库不运行用户代码。** | 收录的第三方仓库永远不会被 clone 后执行、不被 `npm install`、不被构建。索引只保存元数据与链接 |
| **没有后端服务。** | 项目不提供 API、不托管模型、不代为下载资源，不存在“本站被入侵导致用户数据泄露”这类风险 |
| **没有用户账号体系。** | 除 GitHub 自身身份外，本项目不收集、不存储任何个人信息 |
| **自动化只读 GitHub 官方 API。** | 抓取、刷新都走 `api.github.com`，不使用第三方数据源、不爬取网页 |
| **README 是生成物。** | 读者看到的清单由本地脚本从 `data/` 生成，非运行期动态渲染 |

因此以下情形**不属于**本项目漏洞：

- 某个被收录仓库自身存在漏洞或恶意代码（那是上游问题，请报告给上游；但若你发现它其实是恶意的，见第 6.2 节，我们会移除条目）；
- 某个被收录仓库已经 404、被归档、改了名（那是数据陈旧，走 `report-correction.yml`）；
- README 中链接指向的第三方站点挂了或有广告；
- GitHub 平台本身的问题（请报告给 GitHub）。

属于本项目漏洞的典型情形：

- 生成脚本存在路径穿越、命令注入，可被恶意仓库名/描述触发；
- 自动化工作流可被外部输入（Issue 标题、仓库描述、`full_name`）注入命令或篡改数据文件；
- 数据处理逻辑可被构造的 `full_name` / 仓库描述绕过收录标准，把无关仓库写入 `listed`；
- 裁决命令（`/approve` 等）的权限校验可被绕过，使无 write/admin 权限的用户触发状态变更；
- 仓库内的令牌、webhook secret 或个人信息被意外提交。

## 2. 我们实际持有的敏感面

按“泄露后果”排序：

| 资产 | 存放位置 | 泄露后果 |
| --- | --- | --- |
| 自动化用 GitHub Token | 仓库 Secrets（`GITHUB_TOKEN` 或 PAT） | 可写本仓库内容、可读取其可见范围内的仓库、可能触发工作流 |
| 维护者个人账号 | 不在仓库内 | 维护者凭据安全由个人负责（启用 2FA） |
| 数据文件 | `data/**` | 公开，无敏感性；但被篡改会影响索引准确性 |
| Issue/PR 内容 | GitHub | 公开；参与者自行避免在其中粘贴个人信息 |

## 3. 如何报告安全问题

### 3.1 私密渠道（首选）

**请使用 GitHub 的 Private vulnerability reporting**：仓库页面 -> `Security` 标签 -> `Report a vulnerability`。该渠道只有维护者可见。

若该功能不可用，退而使用：给任一维护者发 GitHub 私信，或在 Issue 中只写“我有一个安全问题需要私下报告，请提供联系方式”，**不要在公开 Issue 里描述细节**。

### 3.2 公开渠道（仅限低风险）

可以开公开 Issue 的情形：

- 文档中的安全建议本身有错（例如令牌管理建议不完整）；
- 发现仓库里误提交了**已失效**的凭据（仍请先私信，我们确认失效后再公开讨论）；
- 对安全策略的改进建议。

### 3.3 报告内容建议

```text
受影响部分：脚本 / 工作流 / 数据校验 / 文档
复现步骤：最小可复现步骤，含构造的输入样例
影响：攻击者能做什么（读数据 / 写数据 / 触发工作流 / 其他）
建议修复：可选
```

### 3.4 我们的响应承诺

| 阶段 | 目标时限 |
| --- | --- |
| 确认收到 | 5 个工作日内 |
| 初步评估（是否成立、影响面） | 10 个工作日内 |
| 修复或缓解 | 30 天内，严重问题优先 |
| 公开说明 | 修复发布后，与你协商署名方式 |

我们不会因善意报告而采取法律行动，也不会要求你先签署保密协议。请不要在修复发布前公开细节。

## 4. 令牌与凭据管理

### 4.1 原则

1. **最小权限。** 自动化只需要：读取公开仓库元数据、在本仓库创建/评论 Issue、提交生成后的数据变更。不给 `admin`、不给组织级权限、不给跨仓库写权限。
2. **不写入仓库。** 令牌只存在于 GitHub Actions Secrets，绝不写进 `data/`、`scripts/`、`.env`、示例配置或文档。文档里只用占位符 `${{ secrets.GITHUB_TOKEN }}`。
3. **泄露即轮换。** 无需先判断“是否已被使用”，先轮换再排查。轮换窗口内暂停相关自动化。
4. **能不用 PAT 就不用。** 优先用工作流内置的 `GITHUB_TOKEN`，其权限由 `permissions:` 显式声明且随工作流结束失效。
5. **一人一凭据。** 不为多个维护者共享同一个 PAT；共享凭据无法审计到人。

### 4.2 工作流权限声明示例

每个工作流都应在 job 级别显式声明最小权限，而不是依赖仓库默认：

```yaml
permissions:
  contents: write   # 提交刷新后的数据与 README
  issues: write     # 创建候选 Issue、读取裁决评论
  pull-requests: read
```

不需要的功能一律 `none`/省略。**不要**使用 `permissions: write-all`。

### 4.3 如果你怀疑自己的令牌泄露

1. 立刻在 GitHub Settings -> Developer settings 撤销该 token；
2. 检查该 token 权限范围内的最近操作（Audit log / 仓库提交历史）；
3. 开私密报告告知维护者，说明时间窗口；
4. 由维护者确认数据文件未被篡改，必要时从 git 历史恢复并追加 `changelog.jsonl` 记录。

### 4.4 提交前自检

```bash
# 粗筛常见凭据形态（示例，不保证覆盖全部）
git diff --cached | grep -nEi "(gh[pousr]_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----)"
```

命中即停下，撤回暂存内容并轮换。

## 5. 自动化与供应链

### 5.1 依赖面清单

本项目刻意把供应链面压到最小：

| 组成 | 说明 |
| --- | --- |
| GitHub Actions | **只使用** `actions/checkout` 与 `actions/setup-node` 两个官方 action |
| 第三方 action | **无**。不引入任何 `owner/action@ref` 形式的第三方 action |
| npm 运行时依赖 | **无**。脚本只用 Node.js 内置模块（`node:fs`、`node:fs/promises`、`node:path`、`node:https` 等） |
| 构建步骤 | **无**。脚本直接以 `.mjs` 运行，不经过编译或打包 |

### 5.2 规则

- 引入任何新的第三方 action 或 npm 依赖，都需要在 PR 中单独说明理由，并经 Lead 批准；批量依赖升级类 PR 一律拒绝。
- Action 引用使用官方仓库的稳定大版本或提交 SHA，不使用浮动分支名（`@master`）。
- 工作流不执行来自 Issue/PR 的任意文本作为 shell 命令。`full_name`、仓库描述、Issue 标题在传入 shell 前必须作为参数传递并转义，或以纯文本方式处理（脚本内不拼接 `exec`）。
- 对 `pull_request_target` 保持警惕：它会在有 secrets 的上下文中运行，不得在其中 checkout 并执行 PR 中的代码。
- 不缓存凭据、不把 secrets 写入 artifact、不在日志中 `echo` 任何 token（包括被掩码前的中间值）。

### 5.3 审查要点

Reviewer 审 PR 时至少确认：

1. `data/` 之外只改了必要文件；
2. 工作流 `permissions:` 未被放宽；
3. 新增的 shell 行没有拼接外部输入；
4. 没有新增未申报的依赖或 action。

## 6. 数据完整性与滥用防护

### 6.1 索引被污染

索引的“安全”主要是**准确性安全**。防护措施：

- 只有 write/admin 权限的评论能触发 `/approve`、`/reject`、`/exclude`；
- 每次运行批量上限 20 条，避免单次被灌入大量候选；
- 所有状态变更追加到 `data/state/changelog.jsonl`，可用 git 历史对照；
- `validate.mjs` 检查重复 id、非法分类、缺失证据、README 失同步。

### 6.2 发现被收录仓库是恶意项目

如果某个已收录仓库实际上在做恶意行为（窃取凭据、挖矿、伪装成洛天依相关工具投放恶意载荷），请**私密报告**并给出证据，我们会：

1. 立即把该条目标记为 `excluded`（理由 `malicious`），从 README 移除；
2. 在 `changelog.jsonl` 记录处理过程；
3. 视情况在仓库中发布简短说明，提醒已下载的用户。

我们不会在未经核实的情况下公开指控某个仓库为恶意；但核实门槛是“存在可复现的技术证据”，不是“看起来可疑”。

### 6.3 机器人/爬虫

本项目不托管服务，因此没有限流问题；但自动化抓取 GitHub API 时有速率限制（未认证 60 次/小时，认证 5000 次/小时）。相关策略见 [GOVERNANCE.md](./GOVERNANCE.md) 第 5 节。

## 7. 事件响应流程

1. **接收**：私密渠道收到报告，维护者在 5 个工作日内确认。
2. **分级**：能写数据/能触发工作流/凭据已泄露 = 高；只能在文档层面误导 = 低。
3. **止损**：高优先级先撤销令牌、暂停工作流、回滚可疑提交，再调查。
4. **修复**：改代码或改规则，补一条回归测试。
5. **复盘**：在 `data/state/changelog.jsonl` 或一个私密报告里记录时间线与根因；可按报告者意愿公开。
6. **通知**：若影响第三方（例如某工作流曾向外部宣称某事），主动告知，不隐瞒。

## 8. 支持的版本

本项目是滚动发布的索引仓库，**只维护 `main` 分支的最新状态**。没有版本号，也不为历史快照提供安全更新。

| 分支 | 支持状态 |
| --- | --- |
| `main` | 受支持，安全修复直接合入 |
| 其它分支 / fork | 不受支持 |

如果你从较旧的克隆运行脚本，请先同步 `main`：安全与规则修正不会回迁到旧分支。
