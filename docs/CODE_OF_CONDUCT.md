## 1. 我们的承诺

我们承诺让每个人都能无差别地参与本项目，不因年龄、体型、可见或不可见的残障、族裔、性征、性别认同与表达、经验水平、教育程度、社会经济地位、国籍、外貌、种族、宗教或性取向而受到区别对待。

具体到这个索引项目，承诺意味着三件具体的事：

1. **评价仓库，不评价人。** 我们说“该仓库没有可核验的洛天依相关内容”，不说“提这个的人没做功课”。
2. **对二创作者保持基本尊重。** 收录与否是索引判断，不是对其作品水平的公开评价。
3. **不要求任何人公开身份。** 你不需要说明自己的年龄、职业、是否参与过某个同人组，才能提 Issue。

## 2. 我们的标准

有助于营造良好环境的行为：

- 用事实说明判断：引用 README 原文、文件路径、提交记录，而不是“一看就知道”。
- 接受“未收录”这个结果。收录标准是窄的（见 [CRITERIA.md](./CRITERIA.md)），被排除不等于被否定。
- 在争议中先问“我有没有看错”，再问“对方是不是搞错了”。
- 对新手的问题保持耐心，尤其是他们还不会跑 `node scripts/validate.mjs` 的时候。
- 承认自己错了并修正：维护者的裁决也会错，指出来是贡献，不是攻击。

不可接受的行为：

- 性化语言或 imagery、任何形式的性骚扰；
- 挑衅、侮辱、贬损性评论，人身或政治攻击；
- 公开或私下的骚扰，包括反复私信、跟踪、在无关 Issue 里点名追击；
- 未经明确许可发布他人隐私信息（真实姓名、住址、工作单位、社交账号、聊天记录截图）；
- 其他在职业场合会被认为不当的行为。

针对本项目语境的额外禁止项：

- **冒充官方。** 不得以“Vsinger 官方”“禾念授权”等身份发言或施压；本项目与官方无隶属关系。
- **以举报相威胁。** 不得用“我要去向官方/平台举报你”作为在讨论中获胜的手段。
- **批量骚扰条目作者。** 不得因某仓库未被收录，去该仓库的 Issue 区刷评论、给仓库作者施压。
- **灌水刷榜。** 不得为了让自己或朋友的仓库排到前面而批量提交条目、刷取 star 或在 Issue 里互相 `/approve`。

## 3. 执行责任

维护者（Lead / Reviewer，见 [GOVERNANCE.md](./GOVERNANCE.md)）负责解释与执行本准则，并对举报做出及时、公正的处理。

维护者的具体义务：

- 删除、编辑或拒绝不符合本准则的评论、提交、代码与 Issue；
- 在合理范围内向举报人说明处理结果（不必披露举报人身份）；
- 处理与自己存在利益冲突的案件时回避，交由另一位维护者处理。

维护者滥用本准则（例如用“违反行为准则”封杀正常的收录异议）同样属于违规，可按 [GOVERNANCE.md](./GOVERNANCE.md) 的复审机制提出。

## 4. 适用范围

本准则适用于所有项目空间：

- 本仓库的 Issue、PR、Discussion、Commit 信息与代码注释；
- 与本项目相关的其他场合，当个人**代表本项目**发言时（例如以维护者身份在外部会议、社群、社交媒体上发言）。

不适用于：纯粹私人的对话；以及与本项目无关的第三方仓库内部事务（我们不对他人仓库的社区氛围行使管辖权）。

## 5. 二创与同人内容争议

这是本索引项目最容易产生冲突的地方，单列一节。

### 5.1 三条原则

1. **尊重原作者。** 同人作品、二创模型、翻调音源都有其作者。收录时如实标注仓库自身信息，不替作者宣称授权状态，也不因“同人”而降低对其劳动的基本尊重。
2. **不收录侵权资源。** 以分发盗版音源、未经授权转载的官方美术素材、破解模型为主要内容的仓库不予收录（判定见 [CRITERIA.md](./CRITERIA.md) 排除项与 [NOTICE.md](../NOTICE.md)）。判断标准是“内容主体是否为未授权资源的分发”，而不是“是否涉及版权作品”——所有二创都涉及版权作品，这不是排除理由。
3. **收到权利人通知即下架。** 权利人（含 Vsinger / 上海禾念信息科技有限公司，或具体作品的作者）提出移除请求时，我们**先移除条目、后核实**，不做公开争辩、不要求对方先自证权利。条目移除后进入 `rejected` 或 `excluded`，并在 `data/state/changelog.jsonl` 记录原因。

### 5.2 讨论纪律

涉及二创授权、官方态度、同人边界的讨论中：

- 只陈述可核验事实：官方公告链接、作者声明原文、仓库 LICENSE。
- 不代替官方表态：不说“官方其实是允许的”“官方肯定不会追究”。
- 不替作者表态：不说“作者说过可以商用”。
- 争议未决时，条目可以临时移出 README（状态置 `excluded`，理由写 `under rights review`），等结论明确后再定。

一句话：**索引的责任是准确标注与快速响应，不是替任何人做版权裁决。**

## 6. 执行与处理梯度

按影响与重复性递进，不是一上来就封禁。

| 级别 | 触发情形 | 处理 |
| --- | --- | --- |
| 1. 提醒 | 首次轻微失当：情绪化措辞、跑题争论 | 维护者公开或私下提醒，说明具体是哪句话、为什么 |
| 2. 警告 | 重复失当，或一次明显越界但无恶意 | 正式警告，记录在案；相关评论折叠或删除 |
| 3. 临时限制 | 持续不当、骚扰、公开他人隐私 | 临时禁止参与（Issue / PR / Discussion），期限由处理维护者决定，通常 7–30 天 |
| 4. 永久限制 | 严重违规（性骚扰、威胁、人肉、冒充官方行骗）或临时限制后复发 | 永久禁止参与 |

关于处理方式的说明：

- 拒绝收录、`/reject`、`/exclude` **不是**纪律处分，它们是索引判断，不进入本表。
- 处理决定会记录在案（不含举报人身份信息），可在提出新证据后申请复核。
- 对本准则的执行决定有异议，按 [GOVERNANCE.md](./GOVERNANCE.md) 的维护者会议机制提出，不要在 Issue 里连续刷屏。

## 7. 举报渠道

- **优先**：通过 GitHub 的 [Report abuse](https://github.com/contact/report-abuse) 渠道，或直接私信任一维护者（维护者名单见 `GOVERNANCE.md`）。
- **不要**在公开 Issue 中举报骚扰事件并附上当事人信息，这会二次伤害举报人。
- 举报请尽量提供：发生位置（Issue/PR 链接）、时间、涉及账号、原始内容截图。
- 我们会在收到举报后 **7 天内**给出初步回应。涉及安全漏洞的报告请走 [SECURITY.md](./SECURITY.md) 的私密渠道。
